Midway Auth postMessage Proof of Concept

What This Demonstrates

The vulnerability is in authenticationSuccess() in the login JS: 

function authenticationSuccess(e) {
    showAuthSuccessScreen(e);
    var r = {
        event_type: "auth_success",
        timestamp: Date.now()
    };
    lsTest() && localStorage.setItem("auth_event", JSON.stringify(r));
    window.opener && window.opener.postMessage(r, "*");
    // ...
}

Key Findings:

  • postMessage targetOrigin is "*" - Any origin can receive the message.
  • No opener origin check - The code only checks window.opener exists (truthy check), NOT what origin opened it.
  • Data sent (variable r) contains ONLY: {event_type: "auth_success", timestamp: Date.now()}
  • NO tokens, session data, cookies, or user info are sent via postMessage.
  • Impact is LIMITED: An attacker page can detect WHEN a user successfully authenticates (timing oracle), but does NOT receive any credentials or session tokens.
  • localStorage cross-tab sync: The same event is also written to localStorage with key "auth_event", enabling cross-tab detection of login success.

Severity Assessment:

Low severity. The postMessage with targetOrigin "*" is a CWE-345 (Insufficient Verification of Data Authenticity) issue, but the actual data leaked is only a status event ("auth_success") and a timestamp. No secrets are transmitted. The practical impact is limited to:

  1. An attacker-controlled page can confirm that a user has successfully authenticated to Midway (authentication oracle).
  2. This could be used as a building block in a more complex attack chain (e.g., timing when to attempt CSRF or session-riding attacks).
